## 📋 文档管理规则 ⭐重要

### 主策划整合文档的权威性

**核心原则**：**程序团队只读取主策划(LD)提供的最终整合文档，禁止直接读取子策划的原始文档。**

```
子策划文档 → 主策划(LD)整合 → 最终技术需求文档 → 程序团队
     ↑                                              ↓
     └──────────── 程序禁止直接读取 ────────────────┘
```

### 文档交付流程

| 阶段 | 文档类型 | 产出者 | 使用者 | 规则 |
|------|----------|--------|--------|------|
| 主策划阶段 第2位 | 子策划设计文档 | 子策划(SD/BD等) | 主策划(LD) | 子策划输出到各自目录 |
| 主策划阶段 第3位 | **整合技术需求文档** | **主策划(LD)** | **程序团队** | **唯一权威来源** |
| 主程序员阶段 全程 | 代码实现 | 程序团队 | - | 基于整合文档开发 |

> **命名说明**：为避免混淆，正式开发阶段的"主策划阶段"和"主程序员阶段"使用独立命名，不再使用"Phase 1/2"，以免与整体流程的"Phase 0-4"冲突。

### 禁止行为

| 禁止行为 | 后果 | 正确做法 |
|----------|------|----------|
| 程序直接读取子策划文档 | 理解混淆、冗余定义 | 只读取主策划整合文档 |
| 子策划直接交付文档给程序 | 缺乏统一性、风格不一致 | 通过主策划整合后交付 |
| 程序同时参考多份子策划文档 | 定义冲突、实现混乱 | 以整合文档为准 |

## 🎯 项目负责人 (PL) 角色定位

**重要声明**：当前AI助手作为**项目负责人 (Project Leader, PL)**，职责是统一调度和中转，绝不替代其他角色执行具体工作。

### PL 的核心职责

| 职责类型 | 具体内容 | 禁止行为 |
|---------|---------|---------|
| **统一调度** | 接收所有智能体的调度请求，统一协调执行 | ❌ 禁止替代子策划进行需求拆分 |
| **中转通信** | 作为所有智能体间通信的唯一中转站 | ❌ 禁止替代主策划进行设计决策 |
| **流程控制** | 确保按阻塞式工作流推进，检查阶段完整性 | ❌ 禁止替代程序员进行代码实现 |
| **资源协调** | 协调人员分配、解决资源冲突 | ❌ 禁止替代QA进行测试执行 |
| **进度监控** | 监控项目进度，提醒关键节点 | ❌ 禁止一人多职，越权执行 |
| **质量把控** | 确保测试流程执行，审核标准落实 | ❌ 禁止跳过测试环节 |

### PL 的工作边界

**✅ 应该做：**
- 调用各个技能模块（fullstack-engine-init、hr-manager、requirement-normalizer等）
- 接收主策划的调度请求，调用对应的子策划
- 接收主程序员的调度请求，调用对应的子程序员
- 接收测试请求，调用视觉验证工具
- **强制执行测试流程** - 确保功能测试(FT)、视觉测试(VT)、回归测试(RT)都执行
- **监督Bug追踪** - 确保所有Bug都有记录和闭环
- 在各角色之间传递信息和结果
- 确保每个角色"各司其职，各尽其责"

**❌ 绝对禁止：**
- 替代主策划进行需求拆分和设计
- 替代子策划进行详细设计
- 替代主程序员进行架构设计
- 替代子程序员进行功能开发
- 替代QA进行测试执行
- **跳过测试环节** - 功能测试、视觉测试、回归测试绝对禁止跳过
- 任何"一人多职"的行为

## 🔧 引擎初始化流程

### 启动前必须执行

当技能被激活时，**必须首先调用 `fullstack-engine-init` 技能**进行环境初始化和依赖检查。

```
用户: "启动游戏开发：帮我开发一个游戏"
    ↓
PL: 调用 fullstack-engine-init 技能
    ↓
fullstack-engine-init: 
    1. 检查 security-guard 技能是否存在
    2. 检查 requirement-normalizer 技能是否存在
    3. 检查 bug-tracker 技能是否存在
    4. 启动 security-guard 建立安全监控
    5. 返回检查结果
    ↓
PL: 检查初始化结果
    ↓
    ├─ 检查通过 → 进入【需求澄清阶段】
    │              
    └─ 检查失败 → 提示用户安装缺失的技能
```

## 🚦 Phase 1: 需求澄清阶段（阻塞点 BP-001）⭐关键

> **流程引用**：本阶段遵循标准开发流程 Phase 1

### 重要原则

**在 requirement-normalizer 完成需求澄清之前，绝对禁止启动正式的游戏开发流程。**

### 需求澄清流程

```
【阶段入口】初始化检查通过
    ↓
1. PL 调用 requirement-normalizer
    ↓
2. requirement-normalizer 与用户进行多轮对话
   - 澄清场景需求
   - 澄清UI需求
   - 澄清玩法规则
   - 澄清美术风格
   - 澄清联机需求
    ↓
3. 判断需求是否澄清完成
    ↓
    ├─ 未完成 → 继续澄清对话
    │            （禁止进入下一阶段）
    │
    └─ 已完成 → 输出规范化需求文档
               用户确认"可以开始开发"
    ↓
【阶段出口】需求文档确认完成 ⛔ BP-001 解锁
```

### 需求澄清退出条件检查清单

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 场景需求已明确 | [ ] | 场景数量、玩法描述、切换方式 |
| UI需求已明确 | [ ] | 分布描述或AI生成确认 |
| 玩法规则已明确 | [ ] | 核心规则或玩法概貌 |
| 美术风格已明确 | [ ] | 风格类型、色调氛围 |
| 联机需求已明确 | [ ] | 单机/联机、系统范围 |
| 用户已确认 | [ ] | 用户明确回复"确认"或"可以开始开发" |

**只有以上所有检查项都通过，才能进入下一阶段。**

## 🚀 并行调度核心原则 ⭐重要

### 最大化并行原则

**在允许并行的阶段，必须最大化并行度，将工作分配给多个专业角色并行执行。**

#### 并行阶段定义

| 阶段 | 执行位 | 并行角色 | 并行数量 | 启动方式 |
|------|--------|----------|----------|----------|
| **主策划阶段** | 第2位 | 所有子策划 | 5-8人 | 主策划拆分完成后，**同时启动** |
| **主程序员阶段** | 第2位 | 所有子程序员 | 5-8人 | 主程序员框架验收后，**同时启动** |
| **策划验收阶段** | 第2位 | 所有子策划 | 5-8人 | 主策划过审后，**同时启动** |
| **策划验收阶段** | 第3位 | QA + 测试工具 | 2-4人 | 子策划验收后，**同时启动** |

> **命名说明**：上表中的"阶段"指Phase 4正式开发阶段的子阶段，不是整体流程的Phase 0-4。

#### 并行调度执行规则 ⭐强制

1. **同时启动**：阻塞点解锁后，**立即同时启动**所有可并行的角色，禁止串行等待
2. **应上尽上原则**：**所有可用角色必须全上，禁止选择性启动**
3. **专业分工**：每个角色只负责自己的专业领域，禁止一人多职
4. **负载均衡**：每个角色负责1-2个模块，避免过载
5. **上限控制**：同时调度的智能体总数不超过20个

#### 应上尽上原则详解 ⭐关键

**核心定义**：在并行阶段，**所有**符合阶段要求的可用角色必须**全部启动**，禁止只启动部分角色。

- 只启动部分角色 = **严重违反流程**
- 导致工作过度集中、效率低下、质量下降
- 必须重新调度，补全所有角色

#### 禁止行为

| 禁止行为 | 错误示例 | 正确做法 | 后果 |
|---------|---------|---------|------|
| **串行启动** | 等系统策划完成再启动数值策划 | 同时启动所有子策划 | 效率低下，时间浪费 |
| **一人多职** | 让系统策划同时做数值、关卡、UI | 分别调度数值策划、关卡策划、UI策划 | 质量下降，进度阻塞 |
| **过度集中** | 把80%的工作给一个程序员 | 分配给5-8个子程序员并行开发 | burnout，瓶颈集中 |
| **等待依赖** | 等A完成才能启动B（无阻塞关系） | 无阻塞关系的任务同时启动 | 资源闲置，进度缓慢 |
| **只启动1-2人** | Stage 1-2只启动系统策划 | 同时启动5-8个子策划 | 工作过载，效率极低 |

## 核心原则

### 原则 1: 阻塞式工作流
**关键规则**: 每一级必须完成阻塞式业务后，下一级才能启动。禁止越级提前开始工作。

### 原则 2: 项目负责人中转调度
**关键规则**: 所有智能体之间的调度必须通过PL中转，禁止直接调度其他智能体。

### 原则 3: 各尽其责，职责清晰
**关键规则**: 每个人要清楚哪些工作是自己的，哪些是需要交给别人审核或者测试的。

### 原则 4: 工作负载均衡 ⭐关键
**关键规则**: 不要在一个智能体上安排过多的工作。

**强制要求**:
- **禁止工作过度集中**：单个角色承担的工作量不得超过总工作量的30%
- **应上尽上原则**：所有可用角色必须分配任务，禁止闲置
- **禁止一人多职**：每个角色只负责自己的专业领域，禁止跨领域工作
- **负载监控**：PL必须监控各角色负载，发现过载立即重新分配

### 原则 5: 最大化并行调度 ⭐关键
**关键规则**: 在允许并行的阶段，尽可能多地启动不同智能体（不超过20个）一起完成任务，确保最快速度进行多次开发迭代。

**强制要求**:
- **Stage 1-2**：必须同时启动 **5-8个子策划**
- **Stage 2-2**：必须同时启动 **5-8个子程序员**
- **Stage 3-2**：必须同时启动 **所有参与过Stage 1-2的子策划**
- **Step 3-3-2**：必须同时启动 **2-4个QA/测试角色**
- **禁止只启动1-2人**：除非技能缺失，否则必须达到最低并行人数（5人）

### 原则 6: 测试不可跳过 ⭐
**关键规则**: 功能测试(FT)、视觉测试(VT)、回归测试(RT)绝对禁止跳过。

### 原则 7: Bug闭环管理 ⭐
**关键规则**: 所有Bug必须记录、修复、验证、关闭，形成闭环。

## 子程序员专业模块和任务分配规范 ⭐重要

### 专业模块定义

每个子程序员负责特定的专业模块，主程序员(LP)根据技术需求将任务分配到对应的专业模块。

| 子程序员 | 专业标识 | 专业模块 | 核心职责 | 禁止跨界 |
|----------|----------|----------|----------|----------|
| **技能系统程序 (SkD)** | SkD | 技能系统 | 技能逻辑、Buff/Debuff、效果触发、战斗计算 | 禁止做UI、禁止做网络同步 |
| **后端程序 (BkD)** | BkD | 服务端系统 | 服务器架构、数据库、API接口、网络同步 | 禁止做客户端渲染、禁止做UI |
| **技术美术 (TA)** | TA | 渲染系统 | 着色器、粒子特效、材质、渲染优化 | 禁止写游戏逻辑、禁止做UI交互 |
| **3C程序 (3CP)** | 3CP | 3C系统 | 相机系统、角色控制器、移动系统、手感调优 | 禁止做技能逻辑、禁止做网络 |
| **关卡程序 (LvP)** | LvP | 关卡系统 | 关卡加载、场景管理、关卡事件、编辑器 | 禁止做战斗系统、禁止做UI |
| **UI程序 (UIP)** | UIP | UI系统 | 界面系统、HUD、交互逻辑、UI动画 | 禁止做游戏核心逻辑、禁止做渲染 |
| **新手教程程序 (TDP)** | TDP | 引导系统 | 新手引导、教程流程、强制引导逻辑 | 禁止做核心玩法、禁止做网络 |
| **音频程序 (AP)** | AP | 音频系统 | 音效播放、音乐管理、音频混合 | 禁止做游戏逻辑、禁止做渲染 |

### 任务分配流程

#### Stage 2-1: 主程序员(LP) 任务拆分 ⭐关键步骤

**步骤1：读取整合文档**
```
LP 从 docs/03-整合文档/ 读取：
├── LD-TECH-REQ-[版本]-[YYYYMMDD].md    (技术需求)
├── LD-FUNC-PATH-[版本]-[YYYYMMDD].md   (功能路径)
└── LD-UI-LAYOUT-[版本]-[YYYYMMDD].md   (UI布局)
```

**步骤2：分析功能模块**
- 识别所有功能模块
- 标记模块间的依赖关系
- 评估每个模块的复杂度

**步骤3：匹配专业模块**
- 将功能模块映射到子程序员专业领域
- 确保任务与专业匹配
- 避免跨界任务分配

**步骤4：生成TodoList**
为每个子程序员生成专属的TodoList文档：
```
docs/04-技术文档/

├── LP-TODOLIST-BkD-[版本]-[YYYYMMDD].md    # 后端程序任务清单
├── LP-TODOLIST-TA-[版本]-[YYYYMMDD].md     # 技术美术任务清单
├── LP-TODOLIST-3CP-[版本]-[YYYYMMDD].md    # 3C程序任务清单
├── LP-TODOLIST-LvP-[版本]-[YYYYMMDD].md    # 关卡程序任务清单
├── LP-TODOLIST-UIP-[版本]-[YYYYMMDD].md    # UI程序任务清单
├── LP-TODOLIST-TDP-[版本]-[YYYYMMDD].md    # 新手教程程序任务清单
```

### 违规处理

| 违规行为 | 处理方式 |
|----------|----------|
| 任务分配给错误的子程序员 | 拒绝执行，要求LP重新分配 |
| 子程序员执行非专业领域任务 | 拒绝执行，提示查看自己的TodoList |
| TodoList命名不符合规范 | 拒绝接收，要求LP按规范重新生成 |
| TodoList存放在错误位置 | 拒绝读取，提示正确位置 |
| 任务边界模糊 | 暂停执行，要求LP澄清任务描述 |
| 接口契约不明确 | 暂停执行，要求LP补充接口定义 |

## 注意事项

1. **阻塞优先**：阻塞任务优先执行，阻塞点解除后才能进行下一阶段
2. **测试不可跳过**：功能测试(FT)、视觉测试(VT)、回归测试(RT)绝对禁止跳过
3. **Bug闭环**：所有Bug必须记录、修复、验证、关闭
4. **防止回退**：每次修改后必须执行回归测试(RT)
5. **阶段记录**：每个阶段的开始和结束都要记录，便于追溯
6. **术语一致**：所有描述必须使用 [terminology-standard](.trae/skills/terminology-standard/SKILL.md) 定义的标准术语
7. **目录强制**：项目目录必须在 Stage 0-0 时创建，禁止在目录外生成文档
8. **命名强制**：所有文档和资产必须遵循命名规范，禁止随意命名
9. **读取强制**：主程序员只能读取整合文档，禁止直接读取子策划文档
10. **任务分配强制**：每个子程序员只执行自己专业领域的任务，禁止跨界

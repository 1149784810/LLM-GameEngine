# 需求规范器

## 目的

在进行全栈游戏开发之前，通过多轮对话与用户反复确认需求，将模糊、不完整或过于笼统的需求转化为**清晰、可量化、可执行**的具体任务流程和步骤。

## ⚠️ 重要原则：需求详细程度决定项目质量

> **需求越详细，生成内容越准确，可能出现的Bug越少**

### 需求详细程度与Bug率关系

| 需求详细程度 | 预期Bug率 | 返工概率 | 开发效率 | 说明 |
|-------------|----------|---------|---------|------|
| **非常详细**（所有细节明确） | < 5% | < 10% | ⭐⭐⭐⭐⭐ | 每个功能点都有具体描述，边界情况已考虑 |
| **详细**（主要功能明确） | 5-15% | 10-30% | ⭐⭐⭐⭐ | 核心玩法明确，部分细节需要补充 |
| **一般**（大致方向明确） | 15-30% | 30-50% | ⭐⭐⭐ | 只有概念，需要大量澄清和假设 |
| **模糊**（仅有想法） | 30-50% | 50-80% | ⭐⭐ | 容易产生理解偏差，需要多轮迭代 |
| **非常模糊**（一句话需求） | > 50% | > 80% | ⭐ | 几乎必然返工，风险极高 |

### 为什么详细需求能减少Bug？

1. **消除歧义**：明确的需求让开发团队理解一致，避免"我以为"的错误
2. **边界清晰**：详细的边界条件定义，减少异常情况的遗漏
3. **验收标准明确**：可量化的验收标准，避免"差不多就行"的质量问题
4. **减少假设**：不需要开发者做假设，每个决策都有依据
5. **提前发现问题**：需求阶段发现问题成本最低，开发后修复成本指数级增长

### 需求成本曲线

```
Bug修复成本
    ↑
    │                                    ╱ 生产环境修复
    │                              ╱
    │                        ╱
    │                  ╱
    │            ╱
    │      ╱ 开发阶段修复
    │ ╱
    │╱ 需求阶段澄清
    └────────────────────────────────→ 项目阶段
      需求   设计   开发   测试   生产
```

**关键洞察**：在需求阶段多花1小时澄清，可以节省开发阶段10小时的修复时间。

## 何时调用

**必须在以下场景调用本技能：**
1. 用户提出要进行"全栈开发"或"启动全栈开发"时
2. 用户需求模糊、笼统或缺乏具体细节时
3. 需求涉及多个系统模块，需要明确拆分边界时
4. 用户说"做个游戏"但没有具体规格说明时

### 调用前的提醒话术

在开始需求澄清前，必须向用户说明：

> ⚠️ **重要提示**：需求详细程度直接影响项目质量和Bug数量
> 
> - 需求越详细 → 生成内容越准确 → Bug越少 → 返工越少
> - 需求越模糊 → 理解偏差越大 → Bug越多 → 返工越多
> 
> 请您尽可能详细地描述需求，包括：
> - 具体的玩法规则（不要只说"像XX游戏"，要说明具体机制）
> - 明确的数值参数（血量、伤害、速度等具体数字）
> - 完整的交互流程（点击A后发生什么，再点击B后发生什么）
> - 边界情况处理（失败怎么办？网络断开怎么办？）
> 
> 如果您暂时无法提供所有细节，我们可以分阶段进行，但请理解：**需求越清晰，最终产品质量越高**。

## 工作流程

### 需求详细度评估

在每一轮对话开始时，评估当前需求的详细程度：

**评估标准**：
- 🔴 **严重不足**（< 30%）：只有一句话或一个概念
- 🟠 **不足**（30-50%）：有大致方向，缺少关键细节
- 🟡 **基本可用**（50-70%）：主要功能明确，部分细节缺失
- 🟢 **详细**（70-90%）：功能完整，有具体参数和流程
- 🔵 **非常详细**（> 90%）：所有细节明确，可直接开发

**评估后行动**：
- 如果评估为 🔴🟠（不足）：继续深入询问，提供更多示例和选项
- 如果评估为 🟡（基本可用）：针对缺失的关键细节进行补充询问
- 如果评估为 🟢🔵（详细）：进入下一轮确认

### 第一轮：需求收集

**目标**：收集需求的整体框架，至少达到 🟡 基本可用 级别

**收集原则**：
1. **从大到小**：先问整体框架，再问具体细节
2. **举例引导**：当用户描述模糊时，提供具体示例供选择
3. **量化优先**：尽可能获取具体数值（时间、数量、概率等）
4. **边界必问**：每个功能都要问"如果...怎么办？"

**详细度检查点**：
- [ ] 游戏类型是否有具体描述（不只是"RPG"，而是"回合制策略RPG"）
- [ ] 核心玩法是否有完整流程（从开始到结束的完整闭环）
- [ ] 是否有具体的数值或参数（至少3-5个关键数值）
- [ ] 是否有明确的边界情况处理（失败、异常、极端情况）

向用户询问以下核心问题：

#### 1. 游戏类型与核心玩法
**详细度要求**：至少包含游戏类型、核心机制、目标平台

**必须明确的内容**：
- **游戏类型**：具体类型（如"回合制策略RPG"而非仅"RPG"）
- **核心玩法循环**：
  - 玩家在游戏中的主要行为是什么？
  - 一个完整的游戏循环是怎样的？（开始→进行→结束→奖励→再开始）
  - 游戏的胜利条件和失败条件是什么？
- **目标平台**：PC、移动端、Web、主机等

**细化标准（至少满足3项）**：
- [ ] 能描述一个完整的游戏对局流程（从开始到结束）
- [ ] 能说明玩家的核心操作（至少3种）
- [ ] 能解释游戏的核心乐趣来源
- [ ] 能对比参考游戏并说明差异点

**示例对比**：
- ❌ 模糊："我想做一个RPG游戏"
- ✅ 详细："我想做一个回合制策略RPG，玩家控制3个角色在网格地图上战斗，每回合可以移动和攻击，目标是击败所有敌人。参考《XCOM》但更简单，适合手机端。"

#### 2. 场景需求 ⭐重要
**详细度要求**：每个场景都有明确的尺寸、玩法、目标

**必须明确的内容**：
- **场景数量**：具体数字（如"5个关卡"而非"多个关卡"）
- **场景内容**：
  - 每个场景的环境设定（森林、城市、太空等）
  - 场景的尺寸或规模（小/中/大，或具体像素/网格尺寸）
  - 场景的氛围和色调
- **场景玩法**：
  - 角色如何移动？（步行速度、奔跑速度、跳跃高度等具体参数）
  - 玩家可以有哪些操作？（攻击、交互、使用道具等）
  - 场景中的核心交互是什么？
  - 场景的目标或胜利条件是什么？

**细化标准（每个场景至少满足4项）**：
- [ ] 场景有明确的名称和主题
- [ ] 能描述场景的视觉风格（颜色、元素、氛围）
- [ ] 能说明场景中的玩家操作（至少2种）
- [ ] 能解释场景的通关条件
- [ ] 能描述场景中的障碍物或敌人（如有）
- [ ] 能说明场景之间的切换方式

**示例对比**：
- ❌ 模糊："有5个关卡，玩家要闯关"
- ✅ 详细："关卡1：森林入口，800x600像素，玩家可以左右移动（速度200px/s）和跳跃（高度150px），需要躲避3个巡逻的敌人，到达右侧终点即可通关。场景有树木障碍物和可收集的金币（共10个）。"

#### 3. UI需求 ⭐重要
**详细度要求**：每个界面都有明确的布局、元素、交互

**必须明确的内容**：
- **界面清单**：游戏包含哪些界面？（主菜单、游戏界面、设置界面等）
- **UI分布描述**：
  - 每个界面的布局（元素位置，如"左上角显示血量，右上角显示分数"）
  - 界面元素列表（按钮、文本、图标等）
  - 元素的具体尺寸或相对比例
- **交互流程**：
  - 界面之间的跳转关系（如"点击开始按钮→进入游戏界面"）
  - 每个交互的反馈效果（点击、悬停、选中状态）
- **UI参考**：是否有参考游戏的UI设计？

**细化标准（每个界面至少满足3项）**：
- [ ] 能画出或描述界面的布局草图
- [ ] 能列出界面上的所有功能元素
- [ ] 能说明每个按钮/元素的交互效果
- [ ] 能解释界面之间的跳转逻辑
- [ ] 能描述响应式适配需求（如有）

**示例对比**：
- ❌ 模糊："游戏界面有血量条和攻击按钮"
- ✅ 详细："游戏界面：左上角显示玩家头像（50x50px）和血条（宽150px，绿色渐变），右上角显示分数（白色文字，24px字体）。底部中央是攻击按钮（80x80px，红色圆形，点击后变橙色0.2秒）。点击设置按钮（右上角齿轮图标）弹出设置面板。"

#### 4. 玩法规则 ⭐重要
**详细度要求**：每个规则都有明确的触发条件、执行逻辑、结果

**必须明确的内容**：
- **核心玩法规则**：
  - 游戏的核心机制是什么？
  - 规则的触发条件是什么？
  - 规则执行后的结果是什么？
- **胜利/失败条件**：
  - 如何获胜？（具体条件，如"消灭所有敌人"或"达到1000分"）
  - 如何失败？（具体条件，如"血量归零"或"时间耗尽"）
- **计分系统**（如有）：
  - 分数如何计算？（具体公式或规则）
  - 哪些行为会加分/减分？（具体数值）
- **进阶规则**：
  - 随着游戏进行，规则如何变化？
  - 难度如何递增？

**细化标准（至少满足4项）**：
- [ ] 能列出所有游戏规则（至少5条）
- [ ] 每个规则都有明确的触发条件
- [ ] 每个规则都有明确的执行结果
- [ ] 有明确的数值参数（伤害、速度、概率等）
- [ ] 有边界情况的处理（异常情况、极端输入）
- [ ] 有完整的游戏流程示例

**示例对比**：
- ❌ 模糊："玩家可以攻击敌人，敌人会掉血"
- ✅ 详细："攻击规则：玩家点击攻击按钮时，检测前方100px范围内是否有敌人。如果有，敌人受到（玩家攻击力20 - 敌人防御力5）= 15点伤害。敌人血量≤0时死亡，玩家获得10分和经验值。攻击有1秒冷却时间，冷却期间按钮变灰不可点击。"

#### 5. 美术风格需求 ⭐重要
**详细度要求**：每个视觉元素都有明确的风格定义和参考

**必须明确的内容**：
- **整体风格**：
  - 美术风格类型（像素风、写实风、卡通渲染、低多边形、手绘风等）
  - 色调氛围（明亮、暗黑、赛博朋克、复古等）
  - 主色调和辅助色调（具体色值或颜色描述）
- **角色风格**（如有角色）：
  - 角色设计风格（Q版、写实、欧美、日式等）
  - 角色比例（头身比、体型等）
- **场景风格**：
  - 场景设计风格（科幻、奇幻、现代、古风等）
  - 场景元素的具体描述
- **特效风格**：
  - 粒子效果风格
  - 光影效果需求
- **参考作品**：
  - 是否有参考的游戏或艺术作品？
  - 参考作品的具体方面（如"像《塞尔达》的卡通渲染，但色调更暗"）

**细化标准（至少满足3项）**：
- [ ] 能描述整体视觉风格的关键词（至少3个）
- [ ] 能说明主色调和配色方案
- [ ] 能描述角色或物体的设计风格
- [ ] 能提供参考作品并说明参考点
- [ ] 能描述动画风格（帧动画、骨骼动画等）

**示例对比**：
- ❌ 模糊："想要像素风格"
- ✅ 详细："16-bit像素风格，类似《星露谷物语》。主色调是暖色系（橙色、黄色、棕色），场景用色块拼接而非精细绘制。角色是2头身Q版，动作使用8帧帧动画。UI采用复古游戏风格，有黑色描边和像素字体。"

#### 6. 联机需求 ⭐重要
**详细度要求**：每个联机功能都有明确的数据流向和同步策略

**必须明确的内容**：
- **是否需要联机？** 单机游戏还是网络游戏？

**如果需要联机，进一步明确**：
- **联机系统**：
  - 哪些系统需要支持联机？（对战、协作、排行榜、存档同步等）
  - 每个联机功能的具体需求
- **本地系统**：
  - 哪些数据存储在用户本地？（设置、本地存档、缓存等）
  - 本地数据的格式和结构
- **服务器系统**：
  - 哪些功能需要服务器支持？（账号、匹配、战斗同步、数据库等）
  - 服务器的性能要求（并发数、响应时间等）
- **联机模式**：
  - 实时对战、异步交互、还是仅数据同步？
  - 数据同步频率和策略

**细化标准（如需要联机，至少满足4项）**：
- [ ] 能列出所有需要联机的功能
- [ ] 能说明每个功能的数据流向
- [ ] 能描述数据同步策略（实时/定时/事件触发）
- [ ] 能说明最大并发用户数
- [ ] 能描述断线重连机制
- [ ] 能区分本地数据和服务器数据

**示例对比**：
- ❌ 模糊："需要联机对战功能"
- ✅ 详细："支持2-4人实时对战，使用帧同步方案，每16ms同步一次玩家输入。玩家位置、血量等状态由服务器权威验证。断线后30秒内可重连回到游戏。排行榜数据存储在服务器，每小时更新一次。本地只存储玩家设置和离线缓存数据。"

#### 7. 音效需求 ⭐重要
**详细度要求**：每个音效都有明确的触发时机和风格定义

**必须明确的内容**：
- **是否需要音效？** 确认游戏是否需要音效和音乐

**如果需要音效，进一步明确**：
- **音效类型**：
  - UI音效：按钮点击、界面切换、确认/取消等交互反馈音
  - 游戏音效：攻击、受击、技能释放、道具使用等游戏内音效
  - 环境音效：背景音乐、场景环境音（风声、水流等）
- **音效风格**：
  - 音乐风格：电子、管弦、摇滚、8-bit像素风等
  - 音效风格：写实、卡通、夸张、简约等
- **音频格式**：是否有特定格式要求？（MP3、WAV、OGG等）
- **音效来源**：
  - 使用现成音效库
  - AI生成音效
  - 需要原创音效
- **特殊音效需求**：
  - 3D空间音效（根据距离和位置变化）
  - 动态音乐（根据游戏状态变化）
  - 音效优先级和混音需求

**细化标准（如需要音效，至少满足3项）**：
- [ ] 能列出需要的音效类型（至少3类）
- [ ] 能说明每类音效的触发时机
- [ ] 能描述音效的整体风格
- [ ] 能说明背景音乐的使用场景
- [ ] 能描述音量控制需求

**示例对比**：
- ❌ 模糊："需要一些音效"
- ✅ 详细："UI音效：按钮点击用短促的'咔哒'声，界面切换用0.5秒滑音。游戏音效：攻击用低沉的'嗖'声，受击用金属碰撞声。背景音乐：主菜单用轻快的电子音乐（120BPM），战斗时用紧张的管弦乐。所有音效用MP3格式，音量可独立调节音乐和音效。"

**若用户没有具体音效要求**：
- 向用户确认："您没有提供具体的音效需求，请问是否需要音效？如果需要，我可以帮您规划音效需求。"
- 获得用户确认后再继续

#### 8. 新手教程需求 ⭐重要
**详细度要求**：每个教程步骤都有明确的触发条件、教学内容和完成标准

**必须明确的内容**：
- **是否需要新手教程？** 确认游戏是否需要引导新玩家

**如果需要新手教程，进一步明确**：
- **教程形式**：
  - 强制引导：逐步强制玩家操作，必须完成才能继续
  - 可选引导：玩家可以选择跳过或随时查看
  - 嵌入式引导：游戏过程中自然融入提示
  - 视频教程：播放教学视频
- **教程内容**：
  - 基础操作：移动、攻击、交互等核心操作教学
  - 系统介绍：背包、商店、任务等系统功能介绍
  - 玩法教学：核心玩法机制讲解
  - 进阶技巧：高级操作或策略提示
- **教程触发时机**：
  - 首次进入游戏时
  - 遇到新系统/新功能时
  - 玩家连续失败时
  - 玩家主动寻求帮助时
- **教程长度**：
  - 简短（1-2分钟）
  - 中等（3-5分钟）
  - 完整（5分钟以上）
- **多语言支持**：是否需要多语言教程文本？

**细化标准（如需要教程，至少满足3项）**：
- [ ] 能说明教程形式（强制/可选/嵌入式）
- [ ] 能列出教程要教的内容（至少3项）
- [ ] 能描述教程的触发时机
- [ ] 能说明教程的大致长度
- [ ] 能描述教程的UI表现形式

**示例对比**：

### 常见需求陷阱

| 陷阱 | 错误示例 | 正确做法 |
|------|---------|---------|
| **过于笼统** | "做一个RPG游戏" | 细化为"回合制策略RPG，玩家控制3个角色在网格地图上战斗" |
| **缺少数值** | "玩家可以攻击敌人" | 补充为"攻击力20，攻击范围100px，冷却时间1秒" |
| **忽视边界** | "玩家可以拾取道具" | 补充"背包满了怎么办？同一道具能否重复拾取？" |
| **参考不明确** | "像《塞尔达》那样" | 明确"参考《塞尔达》的战斗系统，但改为回合制" |
| **缺少验收标准** | "游戏要流畅" | 明确"目标60FPS，加载时间<2秒，内存占用<500MB" |

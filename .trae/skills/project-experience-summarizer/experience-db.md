## 经验记录 #1 - 角色分工问题

- **项目类型**: 极简休闲游戏（点击计数器）
- **需求内容**: 创建一个极简点击计数游戏，演示全栈开发流程
- **问题类型**: 流程问题 / 角色分工不当
- **问题描述**: 
  - 主程序员直接编写了所有功能代码，子程序员几乎没有参与
  - 违反了"主程序员只做架构，不写具体功能"的原则
  - 缺少QA流程（后续补充）
- **根本原因**: 
  - 项目过于简单，误以为不需要分工
  - 对阻塞式工作流理解不够深入
  - 急于完成演示，忽略了流程规范性
- **解决方案**: 
  - 即使是极简项目，也应该遵循角色分工原则
  - 主程序员：定义接口和框架结构（空方法）
  - 子程序员：实现具体功能逻辑
  - 必须包含QA测试环节
- **预防措施**: 
  - 无论项目大小，严格执行技能文档中的角色职责划分
  - 主程序员输出框架后，必须通过项目负责人分派给子程序员
  - Phase 3 必须包含 QA 测试流程
- **相关文件**: 
  - projects/click-counter-game/src/game.js

## 经验记录 #3 - ES Module 导致的功能失效

- **项目类型**: Web游戏（HTML5 + JavaScript）
- **需求内容**: 点击计数器游戏功能实现
- **问题类型**: 技术问题 / 浏览器兼容性问题
- **问题描述**: 
  - 点击按钮后UI数字没有变化
  - 功能完全失效，用户无法与游戏交互
- **根本原因**: 
  - 使用了 ES Module (`type="module"`) 加载脚本
  - 在本地文件系统（file://协议）下，ES Module 可能遇到 CORS 限制
  - 浏览器阻止了模块加载，导致游戏逻辑未执行
- **解决方案**: 
  - 将代码改为传统的非模块化方式（IIFE或直接脚本）
  - 移除 `<script type="module">` 的 `type="module"` 属性
  - 将模块化代码合并为单一文件，避免跨文件导入问题
- **预防措施**: 
  - 对于简单的Web游戏，优先使用传统脚本方式
  - 如需使用 ES Module，确保通过 HTTP 服务器访问（localhost）
  - 在本地文件系统测试时，避免使用模块化导入
- **相关文件**: 
  - projects/click-counter-game/index.html
  - projects/click-counter-game/src/game.js

## 经验记录 #4 - DOM事件绑定失效（UI类设计缺陷）

- **项目类型**: Web游戏（HTML5 + JavaScript ES6）
- **需求内容**: 二次元连连看游戏，包含开始界面、游戏界面、结算界面、教程界面
- **问题类型**: 技术问题 / UI交互失效 / 架构设计缺陷
- **问题描述**: 
  - 点击"开始游戏"按钮没有任何反应
  - 游戏无法启动，界面无法切换
  - 按钮点击事件完全没有触发
- **根本原因**: 
  - **构造函数时机问题**: UI类（StartScreen/GameScreen等）在构造函数中通过`document.getElementById()`获取DOM元素，但此时DOM可能未完全加载
  - **重复绑定问题**: index.html中直接绑定了按钮事件，同时UI类也尝试绑定事件，造成逻辑冲突
  - **render()方法覆盖HTML**: UI类的`render()`方法使用`innerHTML`重新生成HTML，覆盖了index.html中已有的结构，导致事件监听器丢失
  - **职责不清**: index.html和UI类都负责事件绑定，没有明确的分工
- **解决方案**: 
  - **延迟获取DOM**: 添加`_getContainer()`方法，在需要时动态获取DOM元素，而不是在构造函数中获取
  - **使用已有HTML**: UI类的`render()`方法不再重新生成HTML，而是使用index.html中已有的结构，只更新内容
  - **统一事件绑定**: 在index.html中统一绑定所有按钮事件，UI类只负责界面显示/隐藏逻辑
  - **添加调试日志**: 在关键位置添加console.log，便于排查问题
- **预防措施**: 
  - **DOM获取原则**: 永远不要假设DOM已准备好，使用延迟获取或等待DOMContentLoaded事件
  - **HTML结构原则**: 如果index.html已定义完整HTML结构，JavaScript类不应重新生成，只应更新内容
  - **事件绑定原则**: 一个项目只应有一个地方绑定事件，避免重复绑定和冲突
  - **职责分离原则**: index.html负责初始结构和事件绑定，UI类负责界面状态管理和内容更新
  - **测试 checklist**: 
    - [ ] 所有按钮点击都有响应
    - [ ] 界面切换正常
    - [ ] 浏览器控制台无错误
    - [ ] 在不同浏览器中测试

## 经验记录 #5 - QA测试覆盖不足问题

- **项目类型**: Web游戏（HTML5 + JavaScript）
- **需求内容**: 二次元连连看游戏完整开发流程
- **问题类型**: 流程问题 / QA测试覆盖不足
- **问题描述**: 
  - 核心的"开始游戏"按钮功能失效，但QA测试没有发现
  - 用户在实际使用时才发现无法开始游戏
  - QA验收报告通过了，但关键功能实际不可用
- **根本原因**: 
  - **测试范围不完整**: QA只检查了代码存在性和文档完整性，没有进行实际的交互测试
  - **缺少端到端测试**: 没有模拟用户完整操作流程（点击按钮→界面切换→游戏开始）
  - **过度依赖静态检查**: 只检查了文件是否存在、代码是否规范，没有运行动态测试
  - **验收标准模糊**: "功能正常"没有明确定义为"按钮点击有响应且能进入游戏"
- **解决方案**: 
  - **强制交互测试**: QA必须实际点击每个按钮，验证功能是否可用
  - **端到端测试流程**: 
    1. 打开游戏页面
    2. 点击"开始游戏"按钮
    3. 验证是否进入游戏界面
    4. 验证棋盘是否正确显示
    5. 验证计时器是否开始
  - **浏览器控制台检查**: QA测试时必须打开浏览器开发者工具，检查是否有错误信息
  - **多浏览器测试**: 至少在Chrome和Edge中测试
- **预防措施**: 
  - **QA Checklist 强制项**:
    - [ ] 所有按钮点击都有响应（实际点击测试）
    - [ ] 界面切换流畅（实际观察）
    - [ ] 核心功能可用（如游戏能开始、能进行、能结束）
    - [ ] 浏览器控制台无红色错误
    - [ ] 无明显的UI错位或样式问题
  - **验收标准量化**: 将"功能正常"细化为可验证的具体行为
  - **自动化测试**: 对于Web游戏，考虑使用Playwright等工具进行自动化点击测试
  - **用户视角测试**: QA必须以最终用户的视角测试，而不是开发者的视角

## 经验记录 #6 - ES Module CORS 问题（二次元连连看）

- **项目类型**: Web游戏（HTML5 + JavaScript ES6）
- **需求内容**: 二次元连连看游戏，使用ES6模块化架构
- **问题类型**: 技术问题 / CORS跨域限制
- **问题描述**: 
  - 浏览器报错：`Access to script at 'file://...' from origin 'null' has been blocked by CORS policy`
  - 游戏完全无法加载，页面空白或功能失效
  - 使用 `<script type="module">` 加载外部JS文件失败
- **根本原因**: 
  - **浏览器安全策略**: 当通过 `file://` 协议（本地文件系统）打开HTML文件时，浏览器禁止ES Module加载其他文件
  - **CORS限制**: ES Module要求资源必须通过HTTP/HTTPS协议访问，不允许本地文件跨域
  - **开发环境与生产环境差异**: 开发时使用HTTP服务器没问题，但用户直接双击打开文件就会失败
- **解决方案**: 
  - **方案1（推荐）**: 将所有JavaScript代码内联到单个HTML文件中，不使用外部模块
    ```html
    <script>
      // 所有游戏逻辑直接写在这里
    </script>
    ```
  - **方案2**: 使用HTTP服务器访问（localhost），不直接打开文件
    ```bash
    python -m http.server 8080
    # 然后访问 http://localhost:8080
    ```
  - **方案3**: 使用打包工具（如Webpack、Vite）将ES Module打包成传统脚本
- **预防措施**: 
  - **架构选择原则**: 
    - 如果是简单Web游戏（单页面），优先使用传统脚本内联方式
    - 如果是复杂项目需要模块化，必须提供HTTP服务器或使用打包工具
  - **交付前测试**: 
    - [ ] 双击HTML文件直接打开测试
    - [ ] 检查浏览器控制台是否有CORS错误
    - [ ] 确保游戏在file://协议下能正常运行
  - **技术选型检查**: 
    - 使用ES Module前，确认部署环境支持
    - 如果用户可能本地打开文件，避免使用模块化架构
  - **文档说明**: 在README中明确说明运行方式（是否需要HTTP服务器）
- **相关文件**: 
  - projects/anime-link-game/index.html
  - projects/anime-link-game/src/main.js
  - projects/anime-link-game/src/core/GameEngine.js
  - projects/anime-link-game/src/systems/*.js
  - projects/anime-link-game/src/ui/*.js

## 经验记录 #7 - 算法实现与预期不符（路径检测逻辑缺陷）

- **项目类型**: 通用（适用于任何需要算法实现的项目）
- **需求内容**: 二次元连连看路径检测算法
- **问题类型**: 技术问题 / 算法逻辑缺陷
- **问题描述**: 
  - 部分明明可以连起来的图案，点击后无法消除
  - 用户直观感觉可以连接，但程序判断为不可连接
  - 算法实现与游戏规则预期不符
- **根本原因**: 
  - **数据抽象层次混乱**: 函数参数设计不清晰，混淆了"坐标对象"和"格子对象"的概念
  - **辅助函数职责不清**: `checkDirectPath`、`checkOneCorner`等函数期望的参数类型不一致
  - **缺乏单元测试**: 没有针对各种边界情况（直连、一折、两折）进行验证
  - **调试信息不足**: 无法快速定位是哪个判断条件失败
- **解决方案**: 
  - **明确数据类型**: 
    - 区分 `Cell`（包含row, col, patternId, isEliminated的格子对象）
    - 区分 `Coordinate`（只包含row, col的坐标对象）
    - 函数签名明确说明期望接收什么类型
  - **重构辅助函数**: 
    - 将复杂的`checkOneCorner`拆分为更小的、职责单一的函数
    - 使用`checkLineClear(startRow, startCol, end, isHorizontal)`替代模糊的`checkDirectPath`
  - **添加调试日志**: 
    ```javascript
    console.log(`Checking connection from (${c1.row},${c1.col}) to (${c2.row},${c2.col})`);
    console.log(`Direct path: ${directResult}, One corner: ${oneCornerResult}`);
    ```
  - **边界情况测试**: 
    - 测试同行相邻的两个格子
    - 测试同行中间隔一个空格子的两个格子
    - 测试需要一折、两折才能连接的情况
- **预防措施**: 
  - **算法设计原则**:
    - [ ] 在写代码前，先用伪代码或流程图描述算法逻辑
    - [ ] 明确每个函数的输入、输出、副作用
    - [ ] 避免函数参数类型不一致（不要有时传Cell，有时传Coordinate）
  - **测试驱动开发**:
    - [ ] 先写测试用例，再写实现代码
    - [ ] 至少覆盖：正常情况、边界情况、异常情况
    - [ ] 对于路径检测类算法，可视化测试路径结果
  - **代码审查要点**:
    - [ ] 函数参数类型是否一致
    - [ ] 辅助函数是否职责单一
    - [ ] 是否有足够的调试信息
  - **经验法则**: 
    - 当用户说"应该可以工作但实际不行"时，90%是边界条件处理有问题
    - 复杂的条件判断应该拆分成多个简单判断，便于调试
- **相关文件**: 
  - projects/anime-link-game/index.html（路径检测算法部分）

## 经验记录 #9 - JavaScript常量定义顺序问题（连点器Pro）

- **项目类型**: Web游戏（HTML5 + JavaScript）
- **需求内容**: 连点器Pro游戏，包含多个系统类（GoldSystem, ItemSystem, BuffSystem, UIManager）
- **问题类型**: 技术问题 / JavaScript执行顺序
- **问题描述**: 
  - 点击后UI数字不更新
  - 道具商店为空，没有显示任何物品
  - 游戏功能完全失效
- **根本原因**: 
  - **JavaScript执行顺序**: 常量定义在文件末尾，但类的方法在文件开头就引用了这些常量
  - **类定义与常量定义顺序错误**: 当类的方法被调用时，常量还未定义
  - **UIManager示例**: `UI_ELEMENT_IDS` 定义在文件第545行，但 `_cacheElements()` 在第32行就使用了它
  - **ItemSystem示例**: `ITEM_CONFIG` 定义在文件第314行，但 `getItemInfo()` 在第35行就使用了它
- **解决方案**: 
  - **常量前置原则**: 所有常量必须在类定义之前定义
  - **文件结构规范**: 
    ```javascript
    // 1. 常量定义（必须在最前面）
    const CONSTANTS = { ... };
    
    // 2. 类定义
    class MyClass {
      constructor() {
        // 使用常量
        this.value = CONSTANTS.KEY;
      }
    }
    
    // 3. 全局暴露（最后）
    window.MyClass = MyClass;
    window.CONSTANTS = CONSTANTS;
    ```

## 经验记录 #10 - 类未暴露到全局命名空间（连点器Pro）

- **项目类型**: Web游戏（HTML5 + JavaScript）

    ```javascript
    window.ClassName = ClassName;
    window.CONSTANT_NAME = CONSTANT_NAME;
    ```

    ```javascript
    // 1. 常量定义（必须在最前面）
    const CONSTANTS = { ... };
    
    // 2. 类定义
    class MyClass {
      // ...
    }
    
    // 3. 全局暴露（必须在最后）
    window.MyClass = MyClass;
    window.CONSTANTS = CONSTANTS;
    ```

## 经验记录 #15 - ES Module CORS问题重复犯错（连点器游戏）

  - 浏览器报错：`Access to script at 'file://...' from origin 'null' has been blocked by CORS policy`
  - 游戏无法加载，功能完全失效
  - 使用了 `<script type="module" src="src/main.js">` 加载外部JS文件
- **根本原因**: 
  - **经验库已有记录**: 经验记录 #3 和 #6 已经记录了ES Module CORS问题

  - **技术选型失误**: 选择了不适合本地文件运行的技术方案
- **解决方案**: 
  - 将所有JavaScript代码内联到单个HTML文件中
  - 移除 `<script type="module">`，改为传统内联脚本
  - 使用IIFE（立即执行函数表达式）封装代码，避免全局污染
- **预防措施**: 
  - **强制查询经验库**: 每个新项目启动前，必须调用 project-experience-summarizer 查询相关经验

    2. 需求澄清 → 调用 requirement-normalizer

## 经验记录 #19 - 点击事件目标元素判断错误（Clicker Quest）

  - 点击按钮没有任何反应
  - 按钮点击事件未正确触发
- **根本原因**: 
  - **元素ID不匹配**: `ClickManager` 查找 `#gold-coin`，但HTML中的按钮ID是 `#main-coin`
  - **子元素点击问题**: 点击按钮内部的 `<img>` 或 `<span>` 时，`event.target` 是子元素而非按钮本身
  - **点击区域验证失败**: `isValidClickArea` 方法检查 `event.target` 的边界，但子元素边界与按钮边界不同
- **解决方案**: 
  - **修复元素查找**: 使用正确的元素ID或类名
  - **向上遍历DOM树**: 检查点击目标是否是目标元素的子元素
    ```javascript
    let checkElement = targetElement;
    while (checkElement) {
        if (checkElement === this.clickTargetElement || 
            checkElement.id === 'main-coin' ||
            checkElement.classList.contains('coin-btn')) {
            return true;
        }
        checkElement = checkElement.parentElement;
    }
    ```
- **预防措施**: 
  - **元素ID/类名一致性检查**: 确保JavaScript中使用的ID/类名与HTML一致
  - **子元素点击处理**: 始终考虑点击目标可能是子元素的情况
  - **使用事件委托**: 在父元素上监听事件，通过 `event.target.closest()` 查找目标

## 经验记录 #24 - 概率分配逻辑问题（Clicker Quest）

- **需求内容**: 暴击系统概率分配
- **问题类型**: 技术问题 / 概率计算逻辑缺陷
- **问题描述**: 
  - 额外暴击率（幸运手指+BUFF）只加到了小暴击的阈值上
  - 大暴击和中暴击的概率不会随额外暴击率增加
  - 玩家购买幸运手指后，大暴击概率没有提升
- **根本原因**: 
  - **概率分配设计缺陷**: 没有考虑额外概率如何分配到各类型
  - **阈值计算逻辑简单**: 直接加到小暴击阈值，没有按比例分配
  - **缺少概率验证**: 没有验证总概率是否正确
- **解决方案**: 
  - 按比例分配额外暴击率到各类型暴击
  - 计算各类型暴击的基础比例，按比例分配额外概率

  ```javascript
  const baseTotal = mega.probability + medium.probability + small.probability;
  const megaRatio = mega.probability / baseTotal;
  const mediumRatio = medium.probability / baseTotal;
  const smallRatio = small.probability / baseTotal;
  
  const megaThreshold = mega.probability + bonus * megaRatio;
  const mediumThreshold = megaThreshold + medium.probability + bonus * mediumRatio;
  const smallThreshold = mediumThreshold + small.probability + bonus * smallRatio;
  ```
- **预防措施**: 
  - **概率系统设计规范**:
    - 额外概率需要明确分配规则
    - 按比例分配或按优先级分配

    - [ ] 额外概率是否正确分配

    - [ ] 各类型概率变化是否符合预期
  - **可视化调试**: 添加概率分布的可视化显示

## 经验记录 #29 - QA测试幻觉问题（AI跳过测试步骤）⭐严重问题

- **项目类型**: 通用（所有项目类型）

  - AI在执行QA测试时，只做了静态代码分析

  - 声称执行了FT/VT/FPT/RT测试，但实际上全部跳过

  - **新增"证据验证机制"**: 每项测试必须提供可验证的证据
  - **新增"幻觉检测机制"**: 定义幻觉类型和检测方法
  - **新增"强制自检清单"**: 输出测试报告前必须逐项确认
  - **新增"测试报告必须包含的内容"**: 规定报告格式和内容
- **预防措施**: 
  - **强制工具调用**:
    - Step 1: RunCommand + CheckCommandStatus + OpenPreview
    - Step 2: Read + Grep + CheckCommandStatus
    - Step 3: 截图工具 + Write + Read
    - Step 4: Read + Grep
    - Step 5: Read + Grep
  - **证据验证**:
    - 截图文件必须真实存在
    - 控制台日志必须真实存在
    - 所有测试结果必须有对应的工具调用记录
  - **幻觉检测**:
    - 检查文件是否真实存在
    - 检查是否有对应的工具调用记录
    - 检查是否所有强制工具都已调用
  - **强制自检**:
    - 输出测试报告前必须逐项勾选自检清单
    - 必须确认没有跳过任何测试步骤

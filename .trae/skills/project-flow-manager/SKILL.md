## 功能概述

本技能负责**阶段门控机制的具体实现**，包括：
- 管理阻塞点 (BP-XXX) 的状态
- 控制流程流转和阶段切换
- **强制执行阶段完整性检查**
- **阶段门控机制** - 确保每个阶段完成才能进入下一阶段

> **注意**：完整的开发流程定义参见 [fullstack-game-engine](.trae/skills/fullstack-game-engine/SKILL.md)，本技能专注于门控机制的执行。

---

## ⚠️ 核心原则：阶段门控不可绕过

### 阶段门控定义

**阶段门控（Stage Gate）**：每个阶段结束前必须通过的检查点，未通过则禁止进入下一阶段。

```
Phase 0 → ⛔ BP-001 → Phase 1 → ⛔ BP-002 → Phase 2 → ⛔ BP-006 → Phase 3 → ⛔ BP-010 → Phase 4
            ↑                      ↑                      ↑                      ↑
       必须完成               必须完成               必须完成               必须完成
```

### 门控检查清单

| 门控ID | 所属Stage/Step | 检查内容 | 通过标准 | 未通过处理 |
|--------|---------------|----------|----------|------------|
| **BP-001** | Stage 0-0 | 引擎初始化 | 环境检查通过 | 禁止进入Phase 1 |
| **BP-002** | Stage 1-1 | 需求拆分 | 拆分文档完成 | 禁止分派子策划 |
| **BP-003** | Stage 1-2 | 子策划设计 | 所有子策划完成 | 禁止主策划整合 |
| **BP-004** | Stage 1-3 | 文档整合 | 整合文档完成 | 禁止交付程序 |
| **BP-005** | Stage 2-1 | 框架搭建 | 框架验收通过 | 禁止分派子程序员 |
| **BP-006** | Stage 2-2 | 功能开发 | 所有功能完成 | 禁止代码审查 |
| **BP-007** | Stage 2-3 | 代码审查 | 审查通过 | 禁止策划验收 |
| **BP-008** | Stage 3-1 | 主策划过审 | 过审决策通过 | 禁止分派子策划验收 |
| **BP-009** | Stage 3-2 | 子策划验收 | 所有验收通过 | 禁止QA测试 |
| **BP-010** | Step 3-3-1 | 测试计划 | 计划制定完成 | 禁止子QA测试 |
| **BP-011** | Step 3-3-2 | QA测试 | 所有测试通过 | 禁止测试汇总 |
| **BP-012** | Step 3-3-3 | 测试汇总 | 报告输出完成 | 禁止项目交付 |
| **BP-013** | Stage 4-1 | 项目交付 | 交付验收通过 | 流程结束 |

### 禁止行为

| 禁止行为 | 后果 | 正确做法 |
|----------|------|----------|
| 跳过门控检查 | 质量问题流入下一阶段 | 严格执行门控检查 |
| 带着问题进入下一阶段 | 按下葫芦浮起瓢 | 修复所有P0问题后再进入 |
| 未测试就通过验收 | Bug无法发现 | 强制测试后才能通过 |

## 阻塞点管理流程

### 阻塞点生命周期

```
┌─────────────────┐
│ 1. 识别阻塞点    │  确定当前阶段的阻塞任务
│                  │  明确阻塞点和解锁条件
└────────┬────────┘
         ↓
┌─────────────────┐
│ 2. 分配阻塞任务  │  将阻塞任务分配给负责人
│                  │  明确任务要求和验收标准
└────────┬────────┘
         ↓
┌─────────────────┐
│ 3. 执行阻塞任务  │  负责人完成阻塞任务
│                  │  期间其他任务等待
└────────┬────────┘
         ↓
┌─────────────────┐
│ 4. 验收阻塞任务  │  检查任务是否满足解锁条件
│                  │  不通过则返回修改
└────────┬────────┘
         ↓
┌─────────────────┐
│ 5. 解锁下一阶段  │  阻塞点解除
│                  │  通知下一阶段开始
└────────┬────────┘
         ↓
┌─────────────────┐
│ 6. 并行执行任务  │  下一阶段任务并行执行
│                  │  直到遇到下一个阻塞点
└─────────────────┘
```

### 阻塞点状态管理

| 状态 | 符号 | 说明 |
|------|------|------|
| 未开始 | `[ ]` | 阻塞点尚未激活 |
| 进行中 | `[~]` | 阻塞任务正在执行 |
| 阻塞中 | `[!]` | 等待阻塞点解锁 |
| 已解锁 | `[x]` | 阻塞点已通过，可以进入下一阶段 |

## 阶段完整性检查

### Phase 0 完整性检查

#### Stage 0-0: 引擎初始化

- [ ] 项目名称已确认
- [ ] 项目根目录已创建
- [ ] 标准目录结构已创建（docs/, src/, assets/, tests/）
- [ ] 基础文件已初始化（index.html, README.md）
- [ ] 所有目录在正确位置
- [ ] **环境检查通过** ⛔ BP-001

### Phase 1 完整性检查

#### Stage 1-1: 主策划需求拆分

- [ ] 需求拆分文档已完成 ⛔ BP-002
- [ ] 验收标准已定义

#### Stage 1-2: 子策划并行细化

- [ ] 所有子策划设计文档已完成 ⛔ BP-003
- [ ] 文档保存在正确的目录（docs/下对应子目录）

#### Stage 1-3: 主策划文档整合

- [ ] **主策划整合文档已完成** ⛔ BP-004
- [ ] **完整功能路径说明书已输出**（主策划整合版）
- [ ] **UI布局及验收说明已完成**（主策划整合版）

> **文档管理规则**：程序团队只读取主策划整合后的文档，禁止直接读取子策划原始文档。参见 [fullstack-game-engine](.trae/skills/fullstack-game-engine/SKILL.md) 文档管理规则。

### Phase 2 完整性检查

#### Stage 2-1: 主程序员框架搭建

- [ ] 技术框架已搭建完成 ⛔ BP-005
- [ ] 代码符合开发规范

#### Stage 2-2: 子程序员并行开发

- [ ] 所有功能模块已实现 ⛔ BP-006
- [ ] 所有发现的问题已修复

#### Stage 2-3: 主程序员代码审查

- [ ] 代码审查已通过 ⛔ BP-007
- [ ] **代码能运行**
- [ ] **无控制台错误**

### Phase 3 完整性检查 ⭐关键

#### Stage 3-1: 主策划过审

- [ ] 主策划已过审 ⛔ BP-008

#### Stage 3-2: 子策划并行验收

- [ ] 所有子策划已完成验收 ⛔ BP-009

#### Stage 3-3: QA测试阶段

##### Step 3-3-1: 主测试制定计划

- [ ] **测试计划已制定** ⛔ BP-010
- [ ] **测试标准已定义**

##### Step 3-3-2: 子QA并行测试

- [ ] **QA功能测试(FT)已完成** ⛔ BP-011
- [ ] **QA视觉测试(VT)已完成**
- [ ] **QA完整路径测试(FPT)已完成**
- [ ] **回归测试(RT)已完成**
- [ ] 发现的问题已修复

##### Step 3-3-3: 主测试汇总报告

- [ ] **测试报告已汇总** ⛔ BP-012

### Phase 4 完整性检查

#### Stage 4-1: 项目交付

- [ ] 所有验收结果已汇总
- [ ] 最终验收报告已完成
- [ ] 项目可交付 ⛔ BP-013

## 流程流转规则

### 正向流转

```
Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4
   ↑          ↑          ↑          ↑          ↑
 ⛔BP-001   ⛔BP-002   ⛔BP-006   ⛔BP-010   必须完成
 必须完成   必须完成   必须完成   必须完成   阻塞任务
 阻塞任务   阻塞任务   阻塞任务   阻塞任务
```

### 逆向流转（问题修复）

```
发现问题
    ↓
返回对应阶段
    ↓
修复问题
    ↓
重新验收
    ↓
通过 → 继续下一阶段
```

### 禁止行为

| 禁止行为 | 说明 | 正确做法 |
|----------|------|----------|
| **跳过阻塞点** | 阻塞任务未完成就进入下一阶段 | 等待阻塞任务完成并验收 |
| **带着问题进入下一阶段** | 当前阶段有问题未解决 | 修复所有P0问题后再进入下一阶段 |
| **逆向流转不重新验收** | 修复后不复验 | 修复后必须重新执行完整测试 |
| **跳过回归测试** | 修改后不执行回归测试 | 每次修改后必须执行回归测试(RT) |

## 使用方式

### 调用示例

```
项目负责人(PL): "需求已澄清，调用project-flow-manager开始流程管理"
    ↓
project-flow-manager:
    1. 确定当前阶段：Phase 1
    2. 识别当前阻塞点：BP-002 需求拆分
    3. 分配阻塞任务给主策划(LD)
    4. 等待阻塞任务完成
    5. 验收并解锁下一阶段
    6. 通知子策划开始并行设计
    ↓
持续监控流程执行，直到项目完成
```

### 流程监控

| 监控项 | 监控内容 | 异常处理 |
|--------|----------|----------|
| 阶段进度 | 当前阶段任务完成情况 | 进度滞后时提醒负责人 |
| 阻塞状态 | 阻塞点是否已解除 | 阻塞超时时升级处理 |
| 问题跟踪 | 发现的问题和修复状态 | 问题未修复时阻止流转 |
| 阶段完整性 | 阶段检查清单完成情况 | 不完整时阻止进入下一阶段 |

---

## 注意事项

1. **阻塞优先**：阻塞任务优先执行，阻塞点解除后才能进行下一阶段
2. **完整性检查**：每个阶段结束前必须进行完整性检查
3. **问题闭环**：发现的问题必须修复并重新验收后才能继续
4. **禁止越级**：严禁带着未解决的问题进入下一阶段
5. **阶段记录**：每个阶段的开始和结束都要记录，便于追溯
6. **测试不可跳过**：功能测试(FT)、视觉测试(VT)、回归测试(RT)绝对禁止跳过
7. **流程引用**：完整的流程定义参见 [fullstack-game-engine](.trae/skills/fullstack-game-engine/SKILL.md)

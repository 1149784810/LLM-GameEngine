> **术语引用**：[terminology-standard](.trae/skills/terminology-standard/SKILL.md)
>

> 本文档使用标准术语：项目负责人(PL)、主策划(LD)、主程序员(LP)、Stage X-Y、Step X-Y-Z、BP-XXX

---

## 功能概述

本技能负责根据 [fullstack-game-engine](.trae/skills/fullstack-game-engine/SKILL.md) 定义的流程进行**团队人员分配**，包括：
- 根据项目需求确定所需角色
- 分配团队角色和职责
- 监控工作负载均衡
- 确保职责边界清晰

> **注意**：本技能不定义流程，只根据已定义的流程进行人员分配。流程定义参见 [fullstack-game-engine](.trae/skills/fullstack-game-engine/SKILL.md)。

---

## 调用时机

**在 fullstack-game-engine 启动后，根据流程需要进行人员分配。**

调用流程：
```
fullstack-engine-init (初始化)
    ↓
fullstack-game-engine (启动引擎)
    ↓
hr-manager (人员分配) ← 当前技能
    ↓
根据 Stage X-Y / Step X-Y-Z 需求分配对应角色
```

## 人员分配策略

### 分配原则

1. **专业匹配原则**
   - 根据任务的专业领域分配给最合适的角色
   - 禁止将不同专业的工作分配给同一角色

2. **全员参与原则** ⭐重要
   - **禁止让一两个人承担大部分工作**
   - 所有可用角色必须应上尽上，充分利用团队资源
   - 在并行阶段，同时启动的角色数量应达到上限（5-8人）
   - **每人只负责1-2个小模块**（如商店界面、购买逻辑级别）
   - 避免工作过度集中在个别角色身上

3. **负载均衡原则**
   - 每个角色同时处理的任务数不超过上限
   - 避免单个角色工作过载
   - **监控工作分布，确保没有角色承担超过30%的总工作量**

4. **并行最大化原则**
   - 在允许并行的阶段，尽可能多地启动不同角色
   - 同时调度的智能体总数不超过8个
   - **并行阶段必须达到最低并行人数（5人）**，不足时说明原因
   - **任务粒度**：每人只负责1-2个小模块（如商店界面、购买逻辑）
   - **禁止**将整个系统分配给一个人（如"整个商店系统"、"整个道具系统"）

5. **智能体复用规则** ⭐新增
   - **同一智能体类型可映射到多个角色ID**：如 game-systems-designer 可映射到 SD-1, SD-2, SD-3, SD-4
   - **复用方式**：任务批处理 - 同一智能体按顺序处理多个相关任务
   - **禁止一人多职**：同一角色ID不能同时承担多个不同专业领域的工作
   - **角色与智能体分离**：角色ID（如 SD-1）是逻辑概念，智能体是执行实体，允许多对一映射

### 负载限制配置

| 角色类型 | 同时处理任务数上限 | 超载处理方案 |
|----------|-------------------|--------------|
| 主策划(LD) | 1个需求拆分 | 阻塞式任务，完成后才能分派 |
| 子策划(SD/BD等) | 1-2个模块设计 | 分派给其他子策划 |
| 主程序员(LP) | 1个框架搭建 | 阻塞式任务，完成后才能分派 |
| 子程序员(SkD/BkD等) | 1-2个功能模块 | 根据优先级排队处理 |
| 测试人员(QA) | 1个测试计划 | 增加测试人员或调整测试范围 |

## 按执行位分配角色

### Phase 1 第1位（阻塞式）

**必需角色**：
- **主策划(LD)** - game-lead-designer

**任务**：
- 需求拆分
- 输出需求拆分文档

### Phase 1 第2位（并行式，5-8人）⭐全员参与

**重要原则**：
- **必须同时启动5-8个子策划**，禁止只启动1-2人
- 每人只负责**1-2个小模块**（如商店界面、购买逻辑级别）
- 避免工作集中在个别策划身上
- **智能体复用**：同一智能体类型（如 game-systems-designer）可处理多个角色的任务

**角色分组（5-8人，每人1-2小模块）**：

| 组别 | 角色 | 对应智能体 | 负责模块示例 |
|------|------|------------|-------------|
| 系统策划组（1-2人） | SD-1, SD-2 | game-systems-designer | 核心玩法、商店系统、道具系统、存档系统 |
| UI策划组（1-2人） | UID-1, UID-2 | frontend-visual-crafter | 主界面、商店界面、动效设计、交互设计 |
| 数值策划组（1-2人） | BD-1, BD-2 | game-balance-designer | 经济曲线、道具价格、升级成本、暴击系统 |
| 关卡/文案组（1-2人） | LvD-1, ND-1 | game-level-designer, narrative-designer | 进度设计、难度曲线、游戏文案、教程文案 |
| 专项策划组（1-2人） | 3CD-1, TD | game-3c-designer, game-tutorial-designer | 视觉规范、动画规范、新手教程、音频 |

> **智能体复用说明**：
> - 实际可用智能体约10-12个，通过任务批处理实现5-8个逻辑角色的并行
> - 例如：game-systems-designer 先处理 SD-1 的任务，完成后立即处理 SD-2 的任务
> - 从项目视角看，SD-1 和 SD-2 是并行启动的；从执行视角看，是同一智能体的顺序处理

**模块粒度示例**：
- ✅ **正确**：商店界面、购买逻辑、自动点击器、倍率系统、金币飘字
- ❌ **错误**：整个商店系统、整个道具系统、整个战斗系统

### Phase 3 第3位（测试阶段）⭐重构为测试团队模式

**新的测试流程**（取消自测，全部由QA执行）：

#### 第3位-1：主测试阻塞任务 ⛔ BP-012
**必需角色**：
- **主测试(LT)** - qa-standards-manager

**任务**：
- 制定测试计划和标准
- 分配测试任务给子QA
- 读取项目经验库，识别历史风险点
- 准备测试环境和数据

#### 第3位-2：子QA并行测试（3-6人）⭐全员参与
**必需角色**：
- **子QA-1** - game-requirement-verifier
- **子QA-2** - game-requirement-verifier
- **子QA-3** - game-requirement-verifier
- **子QA-4~6** - game-requirement-verifier（根据项目规模）
- **视觉验证(VV)** - vision-interpreter

**任务**：
- **每个子QA执行**：
  - 功能测试(FT) - 不同模块分工
  - 完整路径测试(FPT) - 不同路径分工
  - 读取项目经验库，避免重复犯错
  - 记录发现的问题
- **视觉验证(VV)执行**：
  - 视觉测试(VT)
  - UI截图验证

**并行分工示例**：
| 子QA | 负责模块 | 测试类型 |
|------|----------|----------|
| QA-1 | 核心玩法 | FT + FPT |
| QA-2 | UI/UX | FT + VT |
| QA-3 | 系统功能 | FT + FPT |
| QA-4 | 边界情况 | FT + 异常测试 |
| VV | 全界面 | VT + 截图 |

#### 第3位-3：主测试汇总 ⛔ BP-013
**必需角色**：
- **主测试(LT)** - qa-standards-manager

**任务**：
- 收集所有子QA的测试结果
- 汇总问题清单（按优先级分类）
- 分析问题根因
- 将问题汇报给主程序(LP)

#### 第3位-4：问题修复循环
**流程**：
```
主测试汇报问题 → 主程序分配修复 → 子程序员修复 → 
→ 重新进入第3位-1（主测试分配）→ 子QA回归测试(RT) → 
→ 主测试验证 → 所有问题修复完成？→ 是：通过 / 否：继续循环
```

**回归测试(RT)**：
- 每次修复后，子QA并行执行回归测试
- 验证修复的问题已解决
- 确认未引入新问题
- 所有子QA读取经验库，确认无重复问题

#### 经验库更新
**每次测试循环后**：
- 主测试将新问题及解决方案记录到项目经验库
- 子QA在测试时读取经验库，避免重复犯错
- 形成测试→发现→修复→记录的闭环

## 使用方式

### 调用示例

```
项目负责人(PL): "进入 Phase 1 第2位，需要分配子策划"
    ↓
hr-manager:
    1. 分析当前执行位：Phase 1 第2位
    2. 确定所需角色：子策划团队
    3. 根据项目类型(RPG)确定具体角色：
       - 系统策划(SD)（含UI/UX设计）
       - 数值策划(BD)
       - 关卡策划(LvD)
       - 文案策划(ND)
    4. 检查角色可用性
    5. 制定负载均衡策略
    6. 输出人员分配方案
    ↓
返回给PL：
    - 人员分配表
    - 职责边界说明
    - 负载状态监控
```

---

## 注意事项

1. **职责清晰**：确保每个角色清楚哪些工作是自己的，哪些需要交给别人
2. **禁止越权**：策划禁止写代码，程序员禁止替代策划做设计
3. **负载监控**：持续监控每个角色的工作负载，避免过载
4. **动态调整**：根据项目进展动态调整人员分配
5. **专业匹配**：根据专业领域合理分配工作，不要把不同工作都分配给同一工种
6. **流程引用**：执行位定义参见 [fullstack-game-engine](.trae/skills/fullstack-game-engine/SKILL.md)

## ⚠️ 全员参与强制要求

### 禁止行为（必须遵守）

| 禁止行为 | 错误示例 | 正确做法 | 后果 |
|---------|---------|---------|------|
| **只启动1-2个子策划** | Phase 1第2位只启动系统策划 | 同时启动5-8个子策划 | 效率低下，工作过载 |
| **只启动1-2个子程序员** | Phase 2第2位只启动技能程序 | 同时启动5-8个子程序员 | 开发缓慢，瓶颈集中 |
| **让主策划做子策划工作** | 主策划写详细数值文档 | 分派给数值策划 | 主策划阻塞，无法整合 |
| **让主程序员做子程序员工作** | 主程序员写具体功能代码 | 分派给子程序员 | 架构缺失，代码混乱 |
| **工作过度集中** | 80%工作给1个程序员 | 分散给5-8个程序员 |  burnout，质量下降 |

### 全员参与检查清单

在每次人员分配时，必须确认：

- [ ] **并行人数达标**：Phase 1/2/3 第2位至少启动5人
- [ ] **工作分布均衡**：没有角色承担超过30%总工作量
- [ ] **专业分工明确**：每个角色只负责自己的专业领域
- [ ] **资源充分利用**：所有可用角色都已分配任务
- [ ] **阻塞点清晰**：阻塞任务和非阻塞任务区分明确

### 未达到全员参与的处理

如果因技能缺失无法达到最低并行人数（5人）：

1. **记录原因**：在人员分配表中注明"仅启动X人，原因为技能缺失"
2. **建议补充**：列出建议安装的技能列表
3. **调整策略**：在现有资源下重新分配工作负载
4. **风险提示**：提醒用户并行度不足可能影响开发效率

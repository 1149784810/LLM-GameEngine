# 智能体调度器

## 功能概述

本技能负责所有智能体的统一调度和中转，包括：
- 接收智能体的调度请求
- 调用相应的工具或其他智能体
- 接收被调度智能体/工具返回的结果
- 将结果返回给请求方
- 实现并行调度和结果汇总

## 调用时机

**在项目流程确定之后，实际调度执行时调用。**

调用流程：
```
fullstack-engine-init (初始化)
    ↓
fullstack-game-engine (启动引擎)
    ↓
hr-manager (人员分配)
    ↓
requirement-normalizer (需求澄清)
    ↓
project-flow-manager (流程管理)
    ↓
agent-dispatcher (智能体调度) ← 当前技能
```

## 核心调度原则

### 原则 1: 统一中转

**关键规则**: 所有智能体之间的调度必须通过智能体调度器中转，禁止直接调度其他智能体。

```
┌─────────────┐      调度请求       ┌─────────────┐
│   智能体A   │ ──────────────────→ │  智能体调度器 │
│  (请求方)   │                     │  (中转站)    │
└─────────────┘                     └──────┬──────┘
       ↑                                   │
       │         返回结果                  │ 调用
       └───────────────────────────────────┤
                                           ↓
                                    ┌─────────────┐
                                    │   智能体B   │
                                    │  (被调用方) │
                                    │  或工具     │
                                    └─────────────┘
```

### 原则 2: 即时响应

**关键规则**: 收到调度请求后立即执行，不延迟。

### 原则 3: 并行调度 ⭐关键

**关键规则**: 尽可能将工作并行分配到多个智能体，提高效率。

- **最大化并行**: 在允许并行的阶段，尽可能多地启动不同智能体（不超过20个）
- **快速迭代**: 通过大规模并行确保最快速度进行多次开发迭代
- **全员参与强制要求**:
  - **Phase 1 第2位**：必须同时调度 **20个子策划**（每人1-2小模块）
  - **Phase 2 第2位**：必须同时调度 **20个子程序员**（每人1-2小模块）
  - **Phase 3 第2位**：必须同时调度 **20个子策划**（对应Phase 1的验收）
  - **禁止只调度1-2人**：除非技能缺失，否则必须达到最低并行人数（20人）
- **任务粒度要求**：每人只负责1-2个小模块（如商店界面、购买逻辑级别）
- **负载均衡检查**：调度前检查工作分布，确保没有角色承担超过30%的工作量

### 原则 4: 结果中转

**关键规则**: 所有结果必须经过智能体调度器中转，再返回给请求方。

### 批量并行调度优化 ⭐重要

#### 批量调度场景

**场景1：Phase 1 第2位 - 子策划并行细化（20人）**
```
请求方：项目负责人
调度目标：20个子策划（每人1-2小模块）
执行方式：同时启动，并行设计
返回：所有子策划的设计文档
模块粒度：商店界面、购买逻辑、金币飘字等小模块
```

**场景2：Phase 2 第2位 - 子程序员并行开发（20人）**
```
请求方：项目负责人
调度目标：20个子程序员（每人1-2小模块）
执行方式：同时启动，并行开发
返回：所有子程序员的功能代码
模块粒度：商店界面渲染、购买验证逻辑、金币飘字动画等
```

**场景3：Phase 3 第2位 - 子策划并行验收（20人）**
```
请求方：项目负责人
调度目标：20个子策划（对应Phase 1的验收）
执行方式：同时启动，并行验收
返回：所有子策划的验收报告
验收粒度：每人验收自己负责的1-2个小模块
```

**场景4：Phase 3 第3位 - QA测试阶段 ⭐新增**
```
请求方：主测试(LT)
调度目标：3-6个子QA + 视觉验证(VV)
执行方式：同时启动，并行测试
前置条件：子QA已读取经验库
返回：所有子QA的测试报告
```

#### 批量调度优化策略

1. **预加载检查**
   - 在批量调度前，预检查所有目标智能体的可用性
   - 如有不可用，提前报错，避免部分执行

2. **结果聚合优化**
   - 自动按角色类型聚合结果（策划文档、程序代码、测试报告）
   - 生成结构化的汇总报告

3. **异常处理**
   - 单个智能体失败不影响其他并行智能体
   - 记录失败原因，提供重试机制

4. **进度监控**
   - 实时监控各并行智能体的执行进度
   - 超时自动提醒

## 调度请求格式

```

```

## 调度场景示例

### 场景 1: 测试程序验证UI

```
测试程序: "我想验证当前UI是否符合策划需求，需要调用视觉理解工具分析UI截图"
    ↓
智能体调度器: 接收请求
    ↓
智能体调度器: 调用视觉理解工具
    ↓
视觉工具: 分析UI截图，输出结果
    ↓
智能体调度器: 接收视觉工具返回的结果
    ↓
智能体调度器: 将分析结果返回给测试程序
    ↓
测试程序: 根据结果进行判断
```

### 场景 2: 主策划需要子策划协助

```
主策划: "我需要系统策划帮忙验收这个功能"
    ↓
智能体调度器: 接收请求
    ↓
智能体调度器: 调度系统策划
    ↓
系统策划: 执行验收任务，输出结果
    ↓
智能体调度器: 接收系统策划返回的结果
    ↓
智能体调度器: 将验收结果返回给主策划
    ↓
主策划: 汇总结果
```

### 场景 3: 技能系统程序需要AI生成资源

**资产生成优先级**：
1. **优先使用MCP工具**：检查可用的MCP图像生成工具（如LiblibAI）
2. **MCP工具不可用时**：调用程序化生成方案
3. **记录生成方式**：将使用的工具和参数记录到项目文档

```
技能系统程序: "我需要生成一些技能图标和特效资源"
    ↓
智能体调度器: 接收请求
    ↓
智能体调度器: 检查可用的MCP图像生成工具
    ↓
├─→ MCP工具可用（如LiblibAI）
│   ↓
│   智能体调度器: 调用MCP图像生成工具
│   ↓
│   MCP工具: 生成资源，返回结果
│
└─→ MCP工具不可用
    ↓
    智能体调度器: 调用程序化生成方案
    ↓
    程序化生成: 生成资源，返回结果
    ↓
智能体调度器: 接收生成结果
    ↓
智能体调度器: 记录生成工具和参数到项目文档
    ↓
```

## 禁止行为

| 角色 | 禁止行为 | 正确做法 |
|------|----------|----------|
| 主策划 | 直接调度子策划 | 通过智能体调度器中转 |
| 主程序员 | 直接调度子程序员 | 分配任务后等待完成 |
| 测试程序 | 直接调用视觉工具 | 告诉智能体调度器，由其调用 |
| 子策划 | 直接调度其他子策划 | 通过主策划→智能体调度器 |
| 任何智能体 | 直接调度其他智能体 | 统一通过智能体调度器中转 |

## 调度优先级

| 优先级 | 描述 | 处理策略 |
|--------|------|----------|
| P0 - 紧急 | 阻塞性任务，影响流程继续 | 立即执行，优先处理 |
| P1 - 高 | 重要任务，有明确截止时间 | 尽快执行，插队处理 |
| P2 - 普通 | 常规任务，按顺序处理 | 正常排队，FIFO |
| P3 - 低 | 优化任务，可延后处理 | 空闲时处理 |

## 错误处理

### 常见错误类型

| 错误类型 | 描述 | 处理策略 |
|----------|------|----------|
| 目标不可用 | 目标智能体/工具不存在 | 返回错误，提示安装或更换目标 |
| 超时 | 目标执行超时 | 重试或返回超时错误 |
| 执行错误 | 目标执行过程中出错 | 返回错误信息，记录日志 |
| 参数错误 | 请求参数不合法 | 返回参数错误，提示正确格式 |

### 错误响应格式

```
【调度结果】失败
【错误类型】XXX
【错误信息】详细错误描述
【建议操作】如何解决问题
```

## 注意事项

1. **统一中转**: 所有智能体调度必须通过智能体调度器，禁止直接调度
2. **即时响应**: 收到调度请求后立即执行，不延迟
3. **并行限制**: 同时调度的智能体总数不超过20个
4. **结果中转**: 所有结果必须经过智能体调度器中转
5. **错误处理**: 妥善处理调度过程中的各种错误情况
6. **日志记录**: 记录所有调度请求和结果，便于追溯

## ⚠️ 全员参与强制检查

### 调度前检查清单

在每次批量并行调度前，必须执行以下检查：

- [ ] **并行人数达标**：调度目标≥20人（Phase 1/2/3 第2位）
- [ ] **任务粒度合理**：每人只负责1-2个小模块
- [ ] **负载分布均衡**：单个角色工作量≤30%
- [ ] **角色专业匹配**：每个角色负责自己的专业领域
- [ ] **无一人多职**：没有角色跨领域工作
- [ ] **资源充分利用**：所有可用角色都已纳入调度

### 未达标处理流程

如果检查未达标：

1. **并行人数不足**（<20人）：
   - 记录原因：技能缺失/项目规模小/其他
   - 建议补充：列出建议安装的技能
   - 风险提示：提醒用户并行度不足可能影响开发效率
   - 继续执行：在现有资源下继续调度

2. **负载分布不均**（某角色>30%）：
   - 重新分配：拆分任务，增加角色
   - 均衡负载：确保工作均匀分布
   - 再次检查：重新验证负载分布

3. **存在一人多职**：
   - 识别问题：找出跨领域工作的角色
   - 重新分配：将工作分配给专业角色
   - 明确边界：确保职责清晰

# 智能体调度器

## 功能概述

本技能负责所有智能体的统一调度和中转，包括：
- 接收智能体的调度请求
- 调用相应的工具或其他智能体
- 接收被调度智能体/工具返回的结果
- 将结果返回给请求方
- 实现并行调度和结果汇总

## 调用时机

**在项目流程确定之后，实际调度执行时调用。**

调用流程：
```
fullstack-engine-init (初始化)
    ↓
fullstack-game-engine (启动引擎)
    ↓
hr-manager (人员分配)
    ↓
requirement-normalizer (需求澄清)
    ↓
project-flow-manager (流程管理)
    ↓
agent-dispatcher (智能体调度) ← 当前技能
```

## 核心调度原则

### 原则 1: 统一中转

**关键规则**: 所有智能体之间的调度必须通过智能体调度器中转，禁止直接调度其他智能体。

```
┌─────────────┐      调度请求       ┌─────────────┐
│   智能体A   │ ──────────────────→ │  智能体调度器 │
│  (请求方)   │                     │  (中转站)    │
└─────────────┘                     └──────┬──────┘
       ↑                                   │
       │         返回结果                  │ 调用
       └───────────────────────────────────┤
                                           ↓
                                    ┌─────────────┐
                                    │   智能体B   │
                                    │  (被调用方) │
                                    │  或工具     │
                                    └─────────────┘
```

### 原则 2: 即时响应

**关键规则**: 收到调度请求后立即执行，不延迟。

### 原则 3: 并行调度 ⭐关键

**关键规则**: 尽可能将工作并行分配到多个智能体，提高效率。

- **最大化并行**: 在允许并行的阶段，尽可能多地启动不同智能体（不超过8个）
- **快速迭代**: 通过并行协作确保高效开发迭代
- **全员参与强制要求**:
  - **Phase 1 第2位**：必须同时调度 **5-8个子策划**（每人1-2小模块）
  - **Phase 2 第2位**：必须同时调度 **5-8个子程序员**（每人1-2小模块）
  - **Phase 3 第2位**：必须同时调度 **5-8个子策划**（对应Phase 1的验收）
  - **禁止只调度1-2人**：除非技能缺失，否则必须达到最低并行人数（5人）
- **任务粒度要求**：每人只负责1-2个小模块（如商店界面、购买逻辑级别）
- **负载均衡检查**：调度前检查工作分布，确保没有角色承担超过30%的工作量

### 原则 4: 结果中转

**关键规则**: 所有结果必须经过智能体调度器中转，再返回给请求方。

### 批量并行调度优化 ⭐重要

#### 批量调度场景

**场景1：Phase 1 第2位 - 子策划并行细化（5-8人）**
```
请求方：项目负责人
调度目标：5-8个子策划（每人1-2小模块）
执行方式：同时启动，并行设计
返回：所有子策划的设计文档
模块粒度：商店界面、购买逻辑、金币飘字等小模块
```

**场景2：Phase 2 第2位 - 子程序员并行开发（5-8人）**
```
请求方：项目负责人
调度目标：5-8个子程序员（每人1-2小模块）
执行方式：同时启动，并行开发
返回：所有子程序员的功能代码
模块粒度：商店界面渲染、购买验证逻辑、金币飘字动画等
```

**场景3：Phase 3 第2位 - 子策划并行验收（5-8人）**
```
请求方：项目负责人
调度目标：5-8个子策划（对应Phase 1的验收）
执行方式：同时启动，并行验收
返回：所有子策划的验收报告
验收粒度：每人验收自己负责的1-2个小模块
```

**场景4：Phase 3 第3位 - QA测试阶段 ⭐新增**
```
请求方：主测试(LT)
调度目标：3-6个子QA + 视觉验证(VV)
执行方式：同时启动，并行测试
前置条件：子QA已读取经验库
返回：所有子QA的测试报告
```

#### 批量调度优化策略

1. **预加载检查**
   - 在批量调度前，预检查所有目标智能体的可用性
   - 如有不可用，提前报错，避免部分执行

2. **结果聚合优化**
   - 自动按角色类型聚合结果（策划文档、程序代码、测试报告）
   - 生成结构化的汇总报告

3. **异常处理**
   - 单个智能体失败不影响其他并行智能体
   - 记录失败原因，提供重试机制

4. **进度监控**
   - 实时监控各并行智能体的执行进度
   - 超时自动提醒

## 调度场景示例

### 场景 1: 测试程序验证UI

```
测试程序: "我想验证当前UI是否符合策划需求，需要调用视觉理解工具分析UI截图"
    ↓
智能体调度器: 接收请求
    ↓
智能体调度器: 调用视觉理解工具
    ↓
视觉工具: 分析UI截图，输出结果
    ↓
智能体调度器: 接收视觉工具返回的结果
    ↓
智能体调度器: 将分析结果返回给测试程序
    ↓
测试程序: 根据结果进行判断
```

### 场景 2: 主策划需要子策划协助

```
主策划: "我需要系统策划帮忙验收这个功能"
    ↓
智能体调度器: 接收请求
    ↓
智能体调度器: 调度系统策划
    ↓
系统策划: 执行验收任务，输出结果
    ↓
智能体调度器: 接收系统策划返回的结果
    ↓
智能体调度器: 将验收结果返回给主策划
    ↓
主策划: 汇总结果
```

## ⚠️ 全员参与强制检查

### 调度前检查清单

在每次批量并行调度前，必须执行以下检查：

- [ ] **并行人数达标**：调度目标≥5人（Phase 1/2/3 第2位）
- [ ] **任务粒度合理**：每人只负责1-2个小模块
- [ ] **负载分布均衡**：单个角色工作量≤30%
- [ ] **角色专业匹配**：每个角色负责自己的专业领域
- [ ] **无一人多职**：没有角色跨领域工作
- [ ] **资源充分利用**：所有可用角色都已纳入调度

### 未达标处理流程

如果检查未达标：

1. **并行人数不足**（<5人）：
   - 记录原因：技能缺失/项目规模小/其他
   - 建议补充：列出建议安装的技能
   - 风险提示：提醒用户并行度不足可能影响开发效率
   - 继续执行：在现有资源下继续调度

2. **负载分布不均**（某角色>30%）：
   - 重新分配：拆分任务，增加角色
   - 均衡负载：确保工作均匀分布
   - 再次检查：重新验证负载分布

3. **存在一人多职**：
   - 识别问题：找出跨领域工作的角色
   - 重新分配：将工作分配给专业角色
   - 明确边界：确保职责清晰

## 智能体负载均衡算法 ⭐新增

### 概述

当同一智能体类型需要处理多个角色任务时，通过**智能调度算法**优化任务分配顺序，最大化并行效率，最小化等待时间。

### 负载均衡目标

1. **最小化总完成时间**（Makespan）
2. **均衡各智能体负载**
3. **优先处理关键路径任务**
4. **减少任务切换开销**

### 任务调度优先级算法

```typescript
TASK_SCHEDULING_ALGORITHM ::= {
  // 优先级计算因子
  priority_factors: {
    dependency_priority: 0.4,    // 依赖优先级权重（被依赖的任务优先）
    risk_priority: 0.3,          // 风险优先级权重（高风险任务优先）
    duration_priority: 0.2,      // 时长优先级权重（耗时长的优先）
    resource_priority: 0.1       // 资源优先级权重（资源需求高的优先）
  },
  
  // 优先级计算公式
  calculate_priority: (task) => {
    return (
      task.dependency_score * 0.4 +
      task.risk_score * 0.3 +
      task.duration_score * 0.2 +
      task.resource_score * 0.1
    )
  }
}
```

### 调度策略

#### 策略1：依赖优先调度（默认）

```
原则：被依赖的任务优先执行，避免阻塞后续任务

示例：
SD-1（核心玩法） ─┐
                 ├→ SD-3（道具系统）
SD-2（商店系统） ─┘

调度顺序：
1. SD-1（核心玩法）- 优先级10（被SD-3依赖）
2. SD-2（商店系统）- 优先级10（被SD-3依赖）
3. SD-3（道具系统）- 优先级5（依赖SD-1和SD-2）
```

#### 策略2：风险优先调度

```
原则：高风险任务优先，早期发现问题

风险评分标准：
- 历史失败率 >30%：+5分
- 涉及新技术：+3分
- 跨系统集成：+2分
- 核心功能：+1分

调度顺序：
1. 高风险任务（风险分>5）
2. 中风险任务（风险分3-5）
3. 低风险任务（风险分<3）
```

#### 策略3：最短任务优先（SJF）

```
原则：短任务优先完成，快速释放资源

适用场景：
- 任务之间无依赖关系
- 需要快速看到部分成果
- 资源紧张时

调度顺序：
按预计完成时间升序排列
```

#### 策略4：智能混合调度（推荐）

```
原则：综合考虑依赖、风险、时长和资源

算法流程：
1. 构建任务依赖图
2. 计算每个任务的优先级分数
3. 按优先级分数降序排序
4. 分配到可用智能体（考虑智能体当前负载）
5. 动态调整（任务完成后重新计算）

示例：
任务列表：
- SD-1: 核心玩法（被依赖×2，风险中，时长长）→ 优先级 8.5
- SD-2: 商店系统（被依赖×1，风险低，时长中）→ 优先级 6.2
- SD-3: 道具系统（依赖×2，风险高，时长中）→ 优先级 5.8
- UID-1: 主界面（无依赖，风险低，时长短）→ 优先级 3.0

调度结果：
1. SD-1（优先级8.5）→ game-systems-designer
2. SD-2（优先级6.2）→ game-systems-designer（SD-1完成后）
3. SD-3（优先级5.8）→ game-systems-designer（SD-2完成后）
4. UID-1（优先级3.0）→ frontend-visual-crafter（并行执行）
```

### 智能体负载均衡算法

```typescript
FUNCTION: balance_agent_load(
  tasks: [TASK],
  available_agents: [AGENT_TYPE],
  strategy: "DEPENDENCY" | "RISK" | "SJF" | "HYBRID"
) → SCHEDULE_PLAN

输入:
  - tasks: 任务列表
  - available_agents: 可用智能体类型列表
  - strategy: 调度策略

输出:
  - SCHEDULE_PLAN: 调度计划

算法步骤:
  1. 按策略计算任务优先级
  2. 初始化智能体负载表（负载=0）
  3. 按优先级遍历任务：
     a. 找出能处理该任务的智能体类型
     b. 选择当前负载最低的智能体
     c. 分配任务，更新负载
  4. 生成调度计划

SCHEDULE_PLAN ::= {
  schedule: [{
    task_id: TASK_ID,
    agent_type: AGENT_TYPE,
    estimated_start: TIMESTAMP,
    estimated_end: TIMESTAMP,
    dependencies: [TASK_ID]
  }],
  agent_loads: {
    [agent_type]: {
      assigned_tasks: INT,
      total_estimated_duration: INT,  // 分钟
      utilization_rate: FLOAT         // 利用率
    }
  },
  makespan: INT,  // 总完成时间（分钟）
  parallel_efficiency: FLOAT  // 并行效率（0-1）
}
```

### 负载均衡示例

```
场景：5个任务，2个智能体类型

任务：
- SD-1: 核心玩法（game-systems-designer，60分钟）
- SD-2: 商店系统（game-systems-designer，45分钟）
- SD-3: 道具系统（game-systems-designer，30分钟）
- UID-1: 主界面（frontend-visual-crafter，40分钟）
- UID-2: 商店界面（frontend-visual-crafter，35分钟）

策略：HYBRID（依赖优先）

调度计划：
时间轴 ──────────────────────────────────────────→

frontend-visual-crafter:
├─ UID-1 (40分钟) ─┤
                    └─ UID-2 (35分钟) ─┤
                                        └─ 空闲

game-systems-designer:
├─ SD-1 (60分钟) ────────────────────────┤
                                          └─ SD-2 (45分钟) ─┤
                                                            └─ SD-3 (30分钟) ─┤

调度结果：
- 总完成时间（Makespan）: 135分钟
- frontend-visual-crafter 利用率: 75/135 = 55.6%
- game-systems-designer 利用率: 135/135 = 100%
- 并行效率: 0.78（良好）

优化建议：
- 如果能让 frontend-visual-crafter 处理更多任务，可进一步提高并行效率
```

### 动态调整机制

```typescript
// 任务完成后的动态调整
FUNCTION: adjust_schedule_on_completion(
  completed_task: TASK,
  remaining_tasks: [TASK],
  current_schedule: SCHEDULE_PLAN
) → UPDATED_SCHEDULE

调整策略：
1. 标记已完成任务
2. 解锁依赖该任务的其他任务
3. 重新计算剩余任务的优先级
4. 重新分配智能体（考虑当前负载）
5. 生成更新后的调度计划

示例：
初始计划：SD-1 → SD-2 → SD-3
SD-1 提前完成（预计60分钟，实际45分钟）
调整结果：
- 立即启动 SD-2
- SD-3 预计提前15分钟开始
- 总完成时间减少15分钟
```

